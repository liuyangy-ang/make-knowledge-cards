# make-knowledge-cards

`make-knowledge-cards` 是一个面向 Codex Skill 环境的文本提炼技能：把用户粘贴的文章，或本地 Markdown/TXT 文件中的内容，整理成便于复习的知识卡片。它通过明确的提取规则帮助减少重复和无关细节，并要求卡片内容以输入材料为依据。

本项目只包含 Skill 指令和界面配置，不包含独立命令行程序、网页服务或图形界面。

## 解决的问题

阅读长文或复习资料时，提炼重点、合并重复内容并整理成统一格式需要花费时间。此 Skill 指导 Codex 将材料提炼为少量、单点、易复习的卡片，同时避免为了凑数而添加原文没有的信息。

## 主要功能

- 接收用户粘贴的文本，或读取本地 `.md` / `.txt` 文件。
- 根据信息密度生成 5–8 张卡片；原文支撑不足时允许少于 5 张，不强行凑数。
- 每张卡片包含标题、核心知识、简明解释、例子或自测问题四部分。
- 合并重复观点，优先保留原文术语和关键表述，不编造来源中没有的事实。
- 对超长文本，在可行时分块处理并去重；无法分块时处理明确截取的部分，并提示用户。
- 不支持网页抓取、PDF 解析、Anki 导入或 GUI。遇到 URL 或 PDF 请求时，会提示用户粘贴文本或提供 TXT/MD 文件路径。
- 极短或没有实质知识点的输入会返回：`输入内容过短，无法生成知识卡片`。

## 安装方法

本 Skill 没有额外运行依赖。使用时需要一个支持 Codex Skills、并能够访问所提供文件的宿主环境。

将 `skills/make-knowledge-cards` 文件夹复制到 Codex 的 Skills 目录（通常为 `%USERPROFILE%\.codex\skills\`；如果设置了 `CODEX_HOME`，则使用对应目录下的 `skills` 文件夹），然后在宿主中重载或重新打开 Skills。

PowerShell 示例（在项目根目录运行）：

```powershell
New-Item -ItemType Directory -Force "$env:USERPROFILE\.codex\skills" | Out-Null
Copy-Item -Recurse .\skills\make-knowledge-cards "$env:USERPROFILE\.codex\skills\"
```

## 使用方法

在支持该 Skill 的 Codex 对话中调用 `$make-knowledge-cards`，然后粘贴文章内容，或提供本地 `.md` / `.txt` 文件路径。例如：

```text
$make-knowledge-cards
请从以下文章提炼复习卡片：
[在此粘贴文章]
```

也可以这样请求读取文件：

```text
$make-knowledge-cards
请处理这个文件：D:\资料\项目管理笔记.md
```

本项目没有独立 Python 包或 CLI 命令可供安装或运行；本地文件读取由宿主环境提供。

## 输入输出示例

以下示例展示一段包含多个明确知识点的短文，以及依据这些信息生成的卡片。实际卡片数量由输入的信息密度决定。

**输入：**

> 项目团队应先明确项目范围，说明需要交付的产品、服务或成果。确认范围后，可将可交付成果逐层分解为工作包，形成工作分解结构（WBS）。范围基准经批准后，项目团队应按基准开展工作。客户提出新需求时，应记录并评估其对范围、进度和成本的影响，按变更流程审批后再更新相关基准。项目团队还需通过检查确认可交付成果满足验收标准。未经批准的额外工作可能造成范围蔓延。

**输出：**

### 范围定义明确项目交付边界
- **核心知识：** 项目范围说明项目需要交付的产品、服务或成果。
- **简明解释：** 先弄清楚项目要交付什么，团队才能按共同认可的边界开展工作。
- **例子或自测问题：** 范围定义要说明项目交付哪些内容？

### WBS 将可交付成果分解为工作包
- **核心知识：** 确认范围后，可将可交付成果逐层分解为工作包，形成工作分解结构（WBS）。
- **简明解释：** 把较大的交付成果拆成较小的工作组成部分，便于进一步安排和管理。
- **例子或自测问题：** WBS 中，交付成果会被逐层分解成什么？

### 范围基准为项目工作提供依据
- **核心知识：** 范围基准经批准后，项目团队应以它为依据开展工作。
- **简明解释：** 已批准的范围基准记录了当前认可的项目范围，团队据此执行。
- **例子或自测问题：** 项目团队开展工作应依据什么？

### 新需求应先走变更流程
- **核心知识：** 客户提出新需求时，应记录并评估其对范围、进度和成本的影响，经变更流程审批后再更新相关基准。
- **简明解释：** 先评估和审批需求带来的影响，再调整项目认可的计划依据。
- **例子或自测问题：** 客户提出新需求后，项目团队在更新基准前要做什么？

### 验收检查有助于控制范围蔓延
- **核心知识：** 项目团队应检查可交付成果是否满足验收标准；未经批准的额外工作可能造成范围蔓延。
- **简明解释：** 按约定标准核对交付内容，并通过变更流程处理新增工作。
- **例子或自测问题：** 未经批准增加工作可能带来什么问题？
